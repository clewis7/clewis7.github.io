No host round trip PyTorch compute and viz

Getting CUDA and wgpu to agree on a buffer, and what nsys had to say about it.

  • CUDA
  • wgpu
  • Profiling

PyTorch tensors live on the GPU. So do the buffers a renderer draws from. Getting a tensor onto the screen, though, usually means a round trip through system memory and back. This post is about getting rid of that trip.

The problem

Drawing a GPU tensor normally costs two PCIe transfers: down through .cpu() and .numpy(), back up when the plotting library uploads it to render. Two transfers for data that never needed to move.

For small tensors the cost is negligible. But it scales with tensor size — a 4096 ✗ 4096 attention matrix in fp32 is 64MB, so a single redraw shuffles 128MB across the bus to display something already sitting in GPU memory. And that's one frame. Visualizing changes to a tensor means paying it again on every update.

The solution

One GPU, two APIs. PyTorch computes through CUDA on NVIDIA cards; the pygfx renderer draws through Vulkan. They can't see each other's memory, but they can be made to share a single allocation. With this framework, the tensor can reach the screen without ever leaving the card.

Three phases: a setup handshake that runs once, a two-operation frame loop, and a teardown that cleans up.

1. Setup: creating a buffer that both APIs can address

Runs once per watched tensor.

  • Allocate an exportable buffer in Vulkan — a patch to wgpu-native adding one entry point, wgpuDeviceCreateExportableBuffer
    • WebGPU is a portable API and exposes no way to export memory, but wgpu ships deliberate escape hatches down to the raw Vulkan device underneath
    • The buffer is marked shareable at creation, with a dedicated allocation: one VkDeviceMemory for exactly one buffer
    • It's then re-wrapped as an ordinary wgpu buffer so pygfx can bind to it
  • Export it as an opaque fd — the driver registers the allocation with the kernel as a file descriptor
  • Import the fd into CUDA — cuImportExternalMemory, then map it to a device pointer
  • Wrap the pointer as a torch tensor — PyTorch's Python API can't wrap a raw device pointer, so it's laundered through cupy's UnownedMemory (borrowing the address, never owning it) and DLPack, a zero-copy exchange protocol that hands torch a tensor whose storage points at that same address

The result: one set of physical VRAM pages with two virtual mappings. A VkBuffer in Vulkan's world, an ordinary-looking CUDA tensor in PyTorch's.

2. Update: propagating model changes to the viz

Two GPU operations per frame.

  • Copy the model tensor into the shared buffer — one fused CUDA kernel does cast, contiguity gather, and relocation in a single pass
  • Signal completion — the renderer must not read the buffer until CUDA has finished writing it (synchronization, RAW hazard)
    • CUDA and Vulkan submit to independent hardware queues with no shared scheduler; without this, the renderer can read a half-written buffer
  • Blit the buffer into the texture
    • The blit converts a linear layout of the shared buffer to the tiled layout textures are sampled from
  • Render — pygfx samples the texture and draws

3. Cleanup: freeing memory and references

  • Destroy CUDA references
    • Drop the torch view and cupy wrappers that reference the shared buffer
    • Destroy the CUDA external memory mapping
  • Destroy Vulkan references
    • Destroy the VkBuffer (does not free the memory)
    • Poll the device so in-flight work retires
  • Free physical memory
    • Free the actual physical pages of the shared buffer memory on the GPU

The results

To find out what the shared path actually buys, I measured the full trip — CUDA tensor to rendered pygfx texture — across three implementations and six tensor sizes.

Three ways to get a tensor onto a texture

  • shared memory — copy into the dual-mapped buffer, then blit into a texture. Two device-side operations, zero host bytes.
  • host (pinned) — device-to-host copy into a persistent pinned buffer, then upload back to the GPU. Page-locked memory lets the DMA engine read it directly, and the buffer is allocated once and reused. This is what a careful implementation looks like, included so the comparison is fair.
  • host (naive) — t.cpu().numpy() every frame: a fresh pageable allocation, which the driver must must stage through an internal pinned buffer before it can DMA.

All three end at the same destination — a real wgpu texture in the format pygfx samples — and all three are synchronous by construction, returning only when the pixels are ready.

Each cell is the median of 100 updates after 20 warmup iterations, with conditions interleaved rather than run in blocks so thermal drift on a laptop can't systematically favor whichever ran first.

Two regimes

<1 MB: both paths are dominated by fixed per-update overhead — the data movement is microseconds either way. Every update pays a constant cost regardless of size: wgpu-py buffer calls, CUDA kernel launch, event sync scheduling, driver command submission. The shared path's floor is ~0.2 ms; the host path's is lower (~0.09 ms) because it makes fewer wgpu API calls and has no event sync. So at 64² and 256², the host round trip wins.

≥1 MB: data movement takes over, and the two paths stop being comparable. The host path is capped by PCIe — roughly 4 GB/s effective, crossed twice. The shared path uses device-local bandwidth instead.

What nsys has to say about it

The benchmark above isolates a single update. To see what that means in practice, I profiled the training demo end to end.

Both runs train the same CNN (shown above) for 500 steps and update the same 122 tiles per step. The only difference is how pixel data reaches the texture.

The naive version does what you'd expect: each tile is pulled to host with .cpu().numpy(), handed to the plotting library, and re-uploaded. That's 61,000 device-to-host copies — 122 tiles ✗ 500 steps exactly.

The zero-copy version has no device-to-host row at all. Not a smaller number: the operation never happens.

The host-to-device row is identical in both, at 10 copies. Those are the one-time dataset preload and model initialization, and they're a useful control — same startup, same training, so the loop is the only thing that differs.

The host-pinned version is omitted here because this section is about whether the copies happen at all, not how fast they are. Pinned memory makes the round trip cheaper; it doesn't remove it.

Limitations

Everything above runs on Linux, on an NVIDIA GPU, with wgpu on its Vulkan backend.

  • Vulkan — of wgpu's backends, Vulkan is the one with external-memory extensions that CUDA knows how to import. Metal and DX12 have their own sharing mechanisms and would each need a separate implementation.
  • Linux — the handle type is OS-specific. Linux passes memory between APIs as an opaque POSIX file descriptor; Windows uses HANDLEs. The mechanism exists on both, but this patch implements the fd variant. Windows support would require implementing the HANDLE variant.
  • NVIDIA — the importing side is CUDA. The export side is vendor-neutral in principle, but AMD and Intel would need HIP or oneAPI equivalents.

Two further caveats worth naming:

  • This process requires a patched wgpu-native. WebGPU exposes no way to export memory, so the two entry points this depends on don't exist upstream.
  • The synchronization is coarse. The CPU waits on a CUDA event before the renderer submits, which works but puts the host in the middle of a GPU-to-GPU handoff. See Appendix.

Appendix

A1

Why can't the renderer see PyTorch's memory? 

t = torch.rand(64, 64, device="cuda")
  • Holds metadata (shape, strides, dtype) and a Storage reference
  • Storage — a typed window over a contiguous byte range
    • NOT a fresh allocation, but a 512-byte-aligned block carved out of a pre-allocated segment
  • A block has three properties, each fatal on its own:
    • Its address is a virtual address in the CUDA context — meaningless to the renderer
    • It's a slice of a larger allocation given by the CUDA caching allocator
    • Its lifetime belongs to the allocator; when t dies the block is recycled into some future tensor (an external mapping could read the wrong tensor)

PyTorch CUDA Caching Allocator: cudaMalloc/cudaFree are expensive driver calls, so PyTorch grabs large segments and sub-allocates from them, recycling aggressively to reduce the number of driver calls.

Why not just export the memory?
  • Exporting the whole segment or a single block isn't an option: cudaMalloc memory has no shareable handle and cannot be given one post-allocation

A2

Synchronization

Problem
  • CUDA and wgpu submit to independent hardware queues with no shared scheduler
  • Copying from CUDA to the shared buffer returns to Python immediately, so the line finishing says nothing about whether the bytes exist yet
  • RAW hazard if the renderer reads the shared buffer before CUDA has finished copying into it
Solution
  • Record a torch.cuda.Event immediately after the copy — a marker in the stream saying "the copy is behind this point"
    • Costs nothing and blocks nothing; recording is not waiting
  • On the renderer side, wait on that event before submitting the blit
    • Streams execute in order, so passing the marker proves the copy completed
    • Only the visualization side ever waits — the model is never blocked
  • This is why emitting an event beats torch.cuda.synchronize(), which waits for everything queued on the device, including the rest of the forward pass

This is coarse synchronization: the CPU is the middleman, so the host thread briefly blocks even though both parties are on the GPU. There may be better ways to handle this completely on the GPU.
