No host round trip PyTorch compute and viz

Getting CUDA and wgpu to agree on a buffer, and what nsys had to say about it.

  • CUDA
  • wgpu
  • Profiling

PyTorch tensors live on the GPU. So do the buffers a renderer draws from. Getting a tensor onto the screen, though, usually means a round trip through system memory and back. This post is about getting rid of that trip.

The problem

Drawing a GPU tensor normally costs two PCIe transfers: down through .cpu() and .numpy(), back up when the plotting library uploads it to render. Two transfers for data that never needed to move.

For small tensors the cost is negligible. But it scales with tensor size — a 4096 ✗ 4096 attention matrix in fp32 is 64MB, so a single redraw shuffles 128MB across the bus to display something already sitting in GPU memory. And that's one frame. Visualizing changes to a tensor means paying it again on every update.

The solution

One GPU, two APIs. PyTorch computes through CUDA on NVIDIA GPU cards; the renderer draws through Vulkan. They can't see each other's memory, but they can be made to share a single allocation. With this framework, the tensor can reach the screen without ever leaving the card.

Three phases: a setup handshake that runs once, a two-operation frame loop, and a teardown that cleans up.
